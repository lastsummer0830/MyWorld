# MyWorld — Hermes project rules

## Scope and authority
- These rules apply only to the `MyWorld` Git repository.
- Priority: latest user instruction > this file > live code, Git, commands, and renders > product documents > legacy controls.
- Do not inspect or modify sibling repositories or import their facts, rules, or artifacts.
- Treat `CLAUDE.md`, `.claude/**`, old agents, hooks, skills, status boards, and generated outputs as evidence until audited; never execute or restore them automatically.

## Start and safety
- Before editing, run `git rev-parse --show-toplevel` and `git status --short --branch` from this repo.
- Preserve all pre-existing dirty changes. Never use reset, restore, clean, rebase, amend, or force push to remove or rewrite them.
- State the current goal, reason, and intended files before making changes.
- Product code, visual, README, and render work is executed by Claude Code through the parent workspace `scripts/run_claude_worker.py`; Hermes contracts the task and independently verifies diffs, commands, and renders.
- If Claude fails or returns no valid result, Hermes reports the failure and does not silently implement the product change itself.
- One bounded user approval covers ordinary edits and verification in that scope.
- Ask again only for deletion, bulk moves, package installation, commit, push, deployment, control-plane changes, or expansion to another repo.
- Never auto-commit, auto-push, back up to a sibling repo, or run inherited notification scripts.

## Product boundary
- `MyWorld` is the current repository/product label; do not silently rename `MyRoom`, `myRoom`, legacy room routes, or the garden rebuild to match it.
- `src/` legacy room/museum code and `src2/` plus `/rebuild` garden code coexist. Verify lineage and user intent before changing names, routes, credits, license meaning, or ownership claims.
- Never convert team or original-project contributions into the user's personal contribution.

## Required skills for visual work
- Load `3d-scene-art-direction` and `myworld-visual-qa` before changing or approving MyWorld 3D visuals.
- Load `ai-agent-control-plane-audit` before changing rules, hooks, agents, skills, plugins, or profile wiring.

## Visual quality gates
- Use `VISUAL_ACCEPTANCE.md` and the active spike README as criteria, but treat actual comparable renders as the primary evidence.
- Use meaningful visual checkpoints chosen for the actual task and iteration; do not force a fixed number of checkpoints or a fixed three-stage sequence.
- Typical checkpoints are the first judgeable render, a major structure revision needing user judgment, and final acceptance, but a task may need fewer or more.
- At each chosen checkpoint Hermes must fresh-render fixed comparable states and attach representative images, route/query, reference, and `VALIDATED|PARTIAL|INVALIDATED` to the current user chat before the next major revision. A capture path alone is not disclosure.
- Show failed renders plainly as evidence. Do not wait for the final summary, and do not promote or claim completion when a chosen checkpoint image was not shown.
- Preserve `/rebuild` as the baseline; use `/rebuild-reset` as a reversible blockout until explicitly promoted.
- The current dog, flowers, trees, pond, bridge, pergola, house, island, clouds, and outer islands are unapproved. Do not restore or lightly polish legacy assets as the default approach.
- Establish the screen-space hierarchy first: pergola/tea table primary at center, pond/bridge secondary at right foreground, house tertiary at left background.
- The three focal masses must form a triangle rather than stack on one screen axis.
- Redesign the island top contour and soil/rock side silhouette together; reject pancake, rounded-board, and clipped-wall results.
- Exclude clouds, outer islands, light columns, motes, fireflies, and small primitive scatter until they independently pass a render gate.
- Missing image references permit composition exploration only; mark final art approval `unverified`.

## Verification
- For each meaningful visual iteration, capture desktop day and night overviews plus close-ups of affected structures at comparable camera conditions.
- Separate code health, runtime/console health, Hermes visual verdict, and user-visible image delivery as four independent checks.
- Check browser console and JavaScript errors separately from the visual verdict.
- Run targeted ESLint while iterating, then `npm run lint`, `npm run build`, and `git diff --check` before completion.
- On WSL, a killed npm parent may leave a repo-local `next-server`; identify the exact MyWorld process and port before terminating it. Do not delete `.next` as a shortcut.
- Stop bounded dev servers at the end of the session and verify the port is free.
- Report visual verdict as `VALIDATED`, `PARTIAL`, or `INVALIDATED`; a passing build never proves visual acceptance.
